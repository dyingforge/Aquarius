# 自进化门禁改造计划：成功证据、质量评测与 Skill 修订

状态：首版代码已实施；真实模型的受控评测样本尚未运行。当前环境未提供 `OPENAI_API_KEY`，因此离线替身测试仅验证流程。实现采用 `release-checklist-v1` 受控工具替身，报告明确不代表真实命令执行或完整任务质量。

## 1. 目标与边界

本轮只补强三件事：

1. 让「成功案例」有可核验的任务结果，而不是从用户消息或工具返回的存在推算成功。
2. 让 Skill 候选在发布前通过独立于合成过程的质量评测；评测结论必须实际阻止不达标的发布。
3. 让已发布 Skill 能基于新证据产生修订候选，经评测、人工批准后形成新版本。

不改变敏感内容处理；不增加自动发布、可执行代码 Skill、向量检索或常驻 Agent。模型继续只提议，当前视图与发布由 TypeScript 门禁决定。Git 仍是唯一长期事实源，SQLite 仍可从 Git 重建。

本计划改变了首版《DESIGN.md》与原始 `PLAN.md` 中「发布不做语义质量评测」的决定。实施相应阶段时，要在同一变更中更新 `DESIGN.md`、`docs/ARCHITECTURE.md`、`docs/REGISTRY.md`、`docs/PROJECT-SPEC.md` 和 `CHANGELOG.md`；保留原始方案作为历史记录。

## 2. 当前基线与必须处理的缺口

- `SkillService.evaluateCandidates()` 把任意用户消息或 `verified` 工具结果计为成功；`generateCandidate()` 也用同一过滤条件选择案例片段。来源真实不等于任务达成。
- `verifyAuthority()` 只要引用用户消息就赋予 `user_explicit`；它没有证明用户原话支持该条具体主张。
- 摄取中的 `duplicate` 强化分支早于 `gate.outcome` 拒绝与审查分支，可能强化本应待审的现有记忆。
- 发布只有静态格式门禁与用户批准；没有任务集、基线对照或可追溯的评测报告。Aquarius 目前也没有执行 Skill 的任务运行器。
- `hasCandidateFor()` 只要发现关联策略的未拒绝 Skill，就永久跳过后续合成。当前发布表以 `skill_id` 为键，修订不能简单创建第二个同名已发布 Skill。

## 3. 固定的数据与判定契约

### 3.1 任务结果不是证据来源

新增可审计的 `CaseOutcome`，绑定 `case_id + strategy_id + attempt_id`，字段至少包括：`result = success | failure | unknown`、结果判定规则 ID、引用的脱敏证据 ID、来源事件 ID、观察时间、评定者类型、被取代的结果 ID。它是**针对某次策略尝试的结果**，不能把「整个线程最后成功」套给线程中所有策略。

结果记录写入记忆 Git 仓库的独立目录，SQLite 只建立查询投影；与其引用的新证据在同一次摄取提交中写入。追加修正结果，不原地覆盖旧结果；同一尝试的有效结果由确定性规则选出。迁移前的旧案例全部视为 `unknown`，不能因已有用户消息或工具成功而自动补成 `success`。独立性继续按根线程计数，同一根线程最多贡献一个成功案例。

首版只接受两类正向结果：① 用户明确确认**该次任务结果**成功，且消息可定位到对应尝试；② 事先登记的任务验收规则通过，例如该任务要求的完整检查集均成功。命令退出码为零、普通用户发言、Agent 自评、单项工具成功均不能单独证明整项任务成功。明确纠错或验收失败记录为 `failure`；证据不足为 `unknown`。矛盾结果进入审查，不自动择优。

把「引用来自用户」与「引用支持主张」分开。模型可提出被支持的主张和原文片段，TypeScript 核对事件 ID、片段原样存在、角色及结果规则；无法用确定性规则证明语义对应的主张降级为推断或待审，不让模型自报的 `user_explicit` 直接生效。单独保留用户明确确认记忆的路径。

### 3.2 Skill 质量报告

新增版本化 `SkillEvaluation`：候选内容哈希、基线 Skill ID/commit/内容哈希、评测集版本与哈希、模型和工具契约版本、每个任务的结果及失败类别、汇总门禁结论、时间与过期条件。报告的可重建摘要进入 Git；运行时临时文件和原始会话不入库。SQLite 可索引报告，但不能成为唯一保存位置。

`pass`、`fail`、`insufficient_evidence`、`stale` 是不同结果。只有与当前候选内容和基线版本完全匹配、并且结论为 `pass` 的报告，才能进入批准流程。用户批准仍需 `expectedHead`，不能替代质量门禁。

### 3.3 稳定 Skill 身份与修订候选

已发布 Skill 的 `skill_id` 和安装名保持稳定；每次修订使用新的 `candidate_id`，并记录 `revises_skill_id`、`base_commit_sha`、`base_content_hash`。修订候选只在候选区，已安装版在批准前不变。其同名检查仅允许指向**同一** Aquarius 管理的基线 Skill，不放宽对外部 Skill 或其他 Aquarius Skill 的冲突检查。

批准修订时，在一个 Git 提交中更新原 `skills/published/<skill_id>.md` 并移除候选；审查决定、评测报告和旧内容仍可追溯。版本号单调递增；回滚也是新版本，记录 `rollback_of`，不把旧版本号重复当作新发布。安装失败遵循现有可重试的投影语义。

## 4. 分阶段实施

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| A：结果证据 | 增加 `CaseOutcome` Git 契约、解析、SQLite 投影与重建；从会话事件提取候选结果并用确定性规则判定；修正 `applySkillGate` 的输入、`evaluateCandidates()` 和合成输入；让 `duplicate` 分支先服从门禁。 | 普通用户消息、无关的成功工具返回和失败任务均不产生成功案例；三个不同根线程的可验证成功仍可触发候选；删库重建后结果与资格不变。 |
| B：评测基础 | 建立脱敏的任务夹具及开发集、回归集、保留集；为首批声明式 Skill 定义正向任务、误触发任务和失败回归的验收规则；实现有界、隔离的评测运行器，记录基线与候选的同条件结果。 | 评测器有自己的校准样本；结果可按版本复现。无法客观执行或判定的 Skill 标为 `insufficient_evidence`，不声称质量提升。 |
| C：质量发布门禁 | 候选生成后排队评测；报告由确定性函数判为通过、失败或证据不足；批准接口及 CLI 展示差异、任务结果与失败项，并在实际发布前重新核验报告哈希、基线和 HEAD。 | 缺报告、旧报告、关键任务失败、误触发或相对基线退化都不能发布；评测失败不影响现有安装；人工批准仍是最后一步。 |
| D：版本迭代 | 将 `hasCandidateFor()` 改为「同一策略/基线最多一个未决修订」；新成功、纠错或失败证据可以触发修订；合成器读取当前发布版与新增证据，输出修订候选；完成稳定 ID 的发布、安装、回滚和审查展示。 | 已发布 Skill 可生成 v2 候选；拒绝或评测失败保留 v1；批准后才安装 v2；再出现新证据可继续生成下一修订；回滚留下新版本和来源。 |

依赖顺序为 A → B → C → D。A 完成后，先复核旧候选资格；旧候选不自动删除或批准，标记为待重新验证。已有已发布 Skill 保持运行，下一次修订才适用新评测门禁。

## 5. 评测门禁的首版口径

- 候选与基线使用相同任务输入、模型快照、工具契约和预算；新 Skill 的基线是「无该 Skill」，修订版的基线是当前已发布版。
- 合成所用根线程不能同时充当保留集。评测至少覆盖：适用任务、相似但不适用任务、曾失败的关键场景。没有足够独立任务或预先确定的判定规则时，结论为 `insufficient_evidence`，先补夹具。
- 每个 `EvaluationCase` 明确给出脱敏任务输入、适用/不适用标签、允许的受控工具、可观察的期望产物和判定器。运行器只接收 Skill 文本与夹具，通过隔离的测试工具运行；不向被测 Agent 提供真实 Git 句柄、shell、用户工作区路径或外部写权限。首个纵向切片采用发布检查类 Skill：工具由测试替身返回预置结果，判定器检查是否正确触发、按顺序请求所需检查并报告失败。其他类别先保持不可评测状态，再逐类增加夹具适配器。
- 硬门禁：所有关键验收和权限边界必须通过；不适用任务不得误触发；修订版不能在已有通过场景退化。首版要求候选相对基线至少修复一个预先登记的失败场景，同时没有新增失败；若基线已经全部通过，候选没有可证实增益，评测不通过。阈值和任务集在运行前固定，由纯函数判定，不能由模型自行宣布。
- 优先用任务产物、测试结果或确定性断言作判定；模型评分只能作为辅助信号。首版若只能验证声明式步骤是否被正确采用，应在报告里写明「未验证真实工具执行结果」。需要真实工具动作的 Skill，须先有隔离且受限的任务夹具，否则不得标为已通过端到端评测。
- 评测不得接触真实记忆仓库写句柄或用户工作区写权限；预算、超时和评测集版本进入报告。运行器出错属于 `insufficient_evidence`，不能按通过处理。

## 6. 关键改动位置与验证

预计触及 `memory/schema.ts`、`memory/repository.ts`、`memory/paths.ts`、`git/memoryStore.ts`、`db/migrations.ts`、`db/sessionStore.ts`、`gates/promotion.ts`、`pipeline/ingest.ts`、`skills/service.ts`、`agents/runtime.ts`、`jobs/`、`service.ts`、CLI 与 HTTP Skill 接口。质量评测和结果判定应分别有独立的纯函数，避免把规则塞进提示词或服务组合根。

验收测试至少覆盖：

1. 三条仅含普通用户消息的独立案例不触发合成；成功工具步骤不能冒充任务成功；纠错与失败阻止晋升。
2. 同一根线程重复成功只计一次；迟到的结果修正以追加记录改变有效结果，重复摄取不产生第二条有效结果或提交。
3. `duplicate` 在门禁为 `review` / `reject` 时不强化 active 记忆。
4. 评测候选与基线的输入完全一致；保留集与合成案例不重叠；缺失、失败、过期报告均拒绝批准。
5. 修订候选不会覆盖 v1；旧 HEAD、旧基线和重复批准无副作用；批准 v2 后 Git、安装文件与发布投影一致；回滚形成可审计的新版本。
6. 删除 SQLite 并重建后，结果证据、评测结论、当前 Skill 版本与可检索集合一致。

每阶段实施后运行 `pnpm typecheck`、`pnpm test`；针对实际评测运行器另保存一次真实模型/受控工具的脱敏样本结果。确定性替身测试只能验证流程，不能证明候选 Skill 在真实任务上更好。

## 7. 发布前必须回答的问题

- 哪些 Skill 类别可以提供客观任务验收？首批只开放这些类别的质量门禁与修订发布。
- 评测集由谁维护，如何确认保留集未被合成器看到？没有这一条件就不报告「提升」。
- 新增质量评测带来的调用成本和延迟上限是多少？评测放在后台任务中，不阻塞普通问答。
- 对旧候选如何展示 `unknown` 成功结果与 `insufficient_evidence` 评测状态？必须给出补充证据或夹具的下一步操作。

这些问题在阶段 B 固定成版本化配置与验收样本；在此之前不把候选质量判断写成已解决。
